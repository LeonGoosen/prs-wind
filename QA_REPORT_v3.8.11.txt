1. REPRODUCIBLE INPUT BOUNCE
============================
At a 375px-wide Chromium viewport, the v3.8.10 header heights during normal
saving states were:
  Saving...                       107px
  Saved locally / checking mirror 129px
  Saved / 2 copies                107px
The variable-width status text squeezed the adjacent brand, changing line
wrapping and therefore moving the content below the sticky header by 22px.
This happened on ordinary autosave transitions, without a route change.

Correction: reserve a fixed 92px by 42px footprint for the saving control.
The complete status is retained in its title; storage error/recovery notices
still show in full. No field is replaced to implement this correction.

Targeted result: all 221 integer viewport widths from 280 to 500px showed zero
header-height or input-top change between those three saving states. A real
Chromium DOM typing test sampled focus, element identity and field position
60 times during slow per-character typing and asynchronous saving. They stayed
stable and the typed value survived the simulated save.

This reproduces and corrects one concrete cause. It does not prove that every
physical Safari keyboard/visual-viewport interaction is resolved. The actual
competition phone still needs the same typing check.

2. CONFIRMED RANGE / SIZE
=========================
Choosing LRF / confirmed now hides and disables both Range uncertainty and
Target-size uncertainty. A short note makes the model interpretation explicit:
the entered range and size are treated as fixed geometry.

Previously entered uncertainty values are retained for switching back to an
unconfirmed quality; they are not silently discarded. While Confirmed is active:
  rangeSigmaM(target) = 0
  targetScaleSample(target, any sample) = 1
The former implicit 0.5m confirmed-range standard deviation is no longer applied.
An explicit old uncertainty value no longer takes precedence over Confirmed.

This removes modeled uncertainty, not physical measurement error in the real
world. It does not remove wind variability, rifle dispersion, muzzle-velocity
variation or other independently enabled terms. WIND HIT and the wind call do
not change solely because of this flag; the secondary IMPACT estimate can.
Estimated and Match book behavior remains unchanged.

3. EXPLICITLY ADDED OBSERVATIONS
===============================
+ OBSERVATION, + TARGET OBSERVATION and the initial row of + ADD POINT now
create a row with USE already checked. An unknown, untouched default still
contributes no evidence. Choosing an observed behaviour/quality activates the
row without an additional checkbox action. A user can still untick USE.

A placeholder created merely by opening the screen remains inactive. Existing
saved observations are not blanket-enabled or reinterpreted. This preserves
the earlier protection against inventing a Long grass observation.

4. MATHEMATICAL REVIEW OF THE REPORTED EXAMPLE
=============================================
Assumptions for this section only:
- 0.4 is the full angular width/diameter in mil, not radius and not metres.
- The 0.3, 0.6 and 0.8 holds are on the same side.
- Ignore vertical and other aiming/dispersion errors initially.
- H is the actually required signed correction, C the net applied correction.

A horizontal hit requires |H - C| <= 0.4/2 = 0.2.
With C = 0.6, the covered required-hold interval is [0.4, 0.8].
The entered MIN/MAX interval is [0.3, 0.8]. Its width is 0.5; the covered part
is 0.4 wide. The interval [0.3, 0.4) is not covered by that centred correction.

GEOMETRIC COVERAGE IS NOT AUTOMATICALLY PROBABILITY
- Uniform H over [0.3, 0.8]: P(hit horizontally) = 0.4/0.5 = 80%.
- Triangular H over [0.3, 0.8], mode 0.6: P(hit horizontally) =
  1 - (0.4-0.3)^2 / ((0.8-0.3)*(0.6-0.3)) = 93.333333...%.
- Illustrative normal H, mean 0.6 and SD 0.3: P(|H-0.6| <= 0.2) =
  erf(0.2/(0.3*sqrt(2))) = 49.50149249...%.
  That normal example has tails outside the entered interval; it is NOT the
  hard-bounded assumption and is NOT claimed as the user's actual distribution.

A selected CALL is an optimizer output, not proof that it is the mode of a
triangular wind distribution. The triangular calculation is an explicitly
labelled illustration, not a model fitted from the four reported numbers.
Those numbers alone identify neither the probability distribution nor the
joint two-dimensional impact distribution.

EDGE AIMING
Using positive correction to the right for this example, define A as the aim
point relative to target centre (negative means left), and D = +0.6 dialled.
Then C = D + A and the accepted H interval is [C-0.2, C+0.2].
  A =  0.0 (centre): C = +0.6, accepted H from +0.4 to +0.8.
  A = -0.1 (inside left): C = +0.5, accepted H from +0.3 to +0.7.
  A = -0.2 (left rim): C = +0.4, accepted H from +0.2 to +0.6.
Mirror the signs for the opposite convention/wind correction side.
Moving the aim point translates the interval; it never increases its width.
Being 0.1 inside the left rim gives 0.3 of plate to the right and 0.1 to the
left: it reallocates the available width rather than creating extra width.

A fixed 0.4-wide interval cannot guarantee coverage of the entire 0.5-wide
entered bracket. A probability near 100% can nevertheless be plausible when
almost all actual wind probability is in the covered window. That conclusion
requires evidence about the distribution or a well-observed shot-time condition.
P(horizontal hit | H is in [0.4,0.8], no other error) is 100% in the ideal
centre-line model; it must not be substituted for the unconditional hit rate.

ROUND TARGET / IMPACT
For a round 0.4-mil gong with fixed geometry, the two-dimensional criterion is:
  (C - H + E_x)^2 + E_y^2 <= 0.2^2.
At vertical offset 0.1 mil, the available horizontal chord is
2*sqrt(0.2^2 - 0.1^2) = 0.346410... mil, not the full 0.4.
A lower IMPACT percentage can therefore be legitimate, but it must be derived
from defensible dispersion, vertical-error and covariance assumptions.
It cannot be determined from MIN/CALL/MAX and target diameter alone.

5. WHAT THE EXISTING SOURCE ACTUALLY DOES
=========================================
evidenceSpeedStats uses heuristic weighted MIN/AVG/MAX evidence and a Gaussian
speed approximation, with a minimum speed SD of 0.6 mph. These summary values
are not a raw measured time-series histogram.
monteCarloRequiredHolds adds angular scatter: 8, 18 or 35 degrees depending on
its concentration score. The 8-degree floor can apply even to a single
consistent entered direction.
stageBaselineHoldAtSpeed extrapolates outside the MIN/MAX anchors, with a
broad safety cap of two bracket spans beyond each endpoint. MIN/MAX on the
screen therefore are NOT hard limits of the sampled wind-hold distribution.

simulateImpactSamplesV3 adds horizontal/vertical group dispersion, range,
muzzle-velocity, environmental and optional aerodynamic-jump terms. Where
solver-derived sensitivities are absent it uses proxy formulae. Several of
those proxy vertical terms reuse the same z3 sample, which imposes correlation
rather than estimating it from the user's measurements. This is a material
modeling assumption to review, not a demonstrated calibration of actual hit rate.
Group-width to sigma conversion also depends on an assumed full-width / 4
mapping; that is not a universal conversion from any measured group size.

These mechanisms explain how percentages can be below geometric bracket
coverage. They do NOT validate the user's exact 50% / 32% report. No probability
has been multiplied upward, clamped to 80/100%, or replaced with an unstated
uniform/triangular model in this build.

Core probability and wind-response functions were source-compared unchanged:
  evidenceSpeedStats, monteCarloRequiredHolds, probabilityInside,
  stageBaselineHoldAtSpeed, prepareHoldResponse, simulateImpactSamplesV3,
  impactProbability2D, optimizeWindHoldV3, optimizeShootSolutionV5,
  insideTarget2D.
Intentional probability-related changes are limited to the two Confirmed
geometry helpers and their validation/UI interpretation described above.

8. NEXT EVIDENCE FOR THE PROBABILITY QUESTION
===========================================
Use the full JSON backup containing the reported stage, with its target geometry,
manual wind inputs, directions/DOF, rifle/ammo snapshot, dispersion/MV inputs,
solver sensitivities, downrange observations and historical corrections. These
are needed to isolate how the actual 50% / 32% result was produced. Reconstructing
other inputs until a synthetic scenario happens to match is not verification.

MathWorks official triangular-distribution documentation; BIPM JCGM 101:2008
